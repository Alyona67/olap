## Повторная загрузка - как не удвоить данные

При каждом запуске `build_db.py` в начале `ddl_duckdb.sql` выполняются команды `DROP TABLE IF EXISTS` для всех 9 таблиц. Это **удаляет старые таблицы и создаёт новые**, поэтому данные **не удваиваются** — каждый запуск даёт чистую витрину.

## SCD2 (лаба 6)

Для справочника `dim_customer` реализована история изменений (SCD2).
В таблице `dim_customer_scd2` добавлены поля: `valid_from` (дата начала действия версии), `valid_to` (дата окончания) и `is_current` (флаг текущей версии).

Как факт попадает в нужную версию на дату события:
При соединении `fact_sales` со справочником `dim_customer_scd2` помимо ключа `customer_id` учитывается дата продажи:
`fact.date_id BETWEEN dim.valid_from AND COALESCE(dim.valid_to, '9999-12-31')`.
Это гарантирует, что старые продажи привяжутся к старой версии клиента (например, «Новый»), а новые — к обновленной («VIP»).


# Обоснование выбора ключей в ClickHouse (лаба 7-8)

Для таблицы фактов `fact_sales` выбран движок `MergeTree` и порядок сортировки `ORDER BY (date_id, store_id, sale_id)`.

Почему именно такой порядок:
1. В начале стоит `date_id` (дата), так как большинство аналитических отчетов строится за определенный период (месяц, квартал, год). ClickHouse будет быстро отсекать ненужные куски данных.
2. На втором месте `store_id` (магазин), потому что частый разрез для отчетов — это выручка по конкретным магазинам или регионам.
3. На третьем месте `sale_id` (чек), чтобы сохранить логическую упорядоченность внутри одного дня и магазина.

Про партиционирование:
В рамках данной лабораторной мы не используем `PARTITION BY`, так как для учебного объема данных (1,5 млн строк) это не дает ощутимого прироста производительности. Однако при росте данных до десятков миллионов строк логично добавить `PARTITION BY toYYYYMM(date_id)` для разбивки по месяцам.
